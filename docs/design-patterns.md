# design-patterns.md — 게임 디자인 패턴 카탈로그 & 적용 지침

> 이 문서는 교과서 요약이 아니라 **"GuideStory의 어디에 무엇을 쓰고, 무엇을 쓰지 않는가"** 의 결정 지침이다.
> 패턴은 목적이 아니라 도구다. 작은 코드에 패턴을 미리 끼워 넣으면 그게 바로 우리가 피하려는 **외계인 코드**가 된다.
> 따라서 각 패턴은 **상태(이미 적용 / 도입 예정 / 보류·금지)** 와 **이 프로젝트에서의 근거**를 함께 적는다.
> 관련: [ARCHITECTURE.md](../ARCHITECTURE.md)(ADR), [PLANS.md](../PLANS.md)(로드맵), [tech-debt-tracker.md](../tech-debt-tracker.md).

## 0. 적용 원칙 (먼저 읽기)

1. **패턴은 통증이 생긴 뒤에 도입한다.** "언젠가 확장될 것"이 아니라 "지금 변경이 아프다"가 신호다. (ADR-003이 명시: 상속으로 시작 → 통증 시점에 컴포넌트 전환)
2. **이미 가진 추상화를 패턴 이름으로 다시 부르지 않는다.** 우리는 이미 `IRenderDevice`/`IWindow`/`Input`(ADR-006), `Screen`/`SceneId`(상태 전이), `MoveIntent`(입력 디커플)를 갖고 있다. 이름표만 붙이는 리팩토링은 하지 않는다.
3. **하나의 통증 = 하나의 패턴.** 동시에 여러 패턴을 얹지 않는다.
4. **트레이드오프를 쓰지 않은 패턴은 도입하지 않는다.** 이 프로젝트의 산출물은 "결정의 근거"다. 패턴을 넣으면 ADR이나 이 문서에 비용까지 기록한다.

| 9 | 데이터 주도 + 플라이웨이트 | 🟡 예정 | P-006, ADR-005 — `DataManager`가 스킬/몬스터 스펙 공유 |

| 11 | 옵저버 / 이벤트 버스 | 🟡 조건부 | HP·점수 등 다대다 알림이 생길 때만. 지금은 금지(2번 원칙) |

| 13 | 빌더(Builder) | 🟡 조건부 | 맵/몬스터 생성 절차가 다단계·다표현이 될 때 |
| 14 | 데커레이터(Decorator) | 🟡 조건부 | 무기/버프 효과 중첩이 생길 때 |
| 15 | 방문자(Visitor) | 🔴 보류 | 타입군이 안정되기 전엔 비용 > 이득 |

| 18 | 싱글톤(Singleton) | 🔴 금지 | 아래 §3.1 참고 — 현재 구조와 충돌 |

## 2. 이미 적용한 패턴 (이름표 정리)

> 새로 만들 것이 아니라, **이미 한 좋은 결정에 패턴 이름을 붙여 두는 것**이다. 신규 작업자가 구조를 빨리 읽도록.

### 2.1 전략(Strategy) + 어댑터(Adapter) — 렌더/입력 추상화
- **무엇**: 게임 로직은 `IRenderDevice`/`IWindow`/`Input`(인터페이스)에만 의존하고, `SDLRenderDevice`/`SDLWindow`가 SDL을 그 인터페이스로 **변환(어댑터)** 한다. 구현체를 통째로 갈아끼울 수 있는 점이 **전략**이다.
- **근거**: ADR-006(SDL 디커플링). SDL2→SDL3/DirectX 이식 시 구현체만 교체.
- **비용**: 우회 호출 1단계. 측정 가능한 수준에서 무시 가능.

### 2.2 상태(State) — 장면 전이
- **무엇**: `Screen`/`EditorScreen`이 한 장면의 입력·렌더를 캡슐화하고, `Update()`가 다음 `SceneId`/`EditorScene`를 반환하면 호스트 루프가 교체한다. `switch`로 장면 행동을 분기하지 않는다.
- **세 글의 "상태 패턴"과의 관계**: 글에서 말한 "상태를 클래스로 캡슐화"가 정확히 이것. 다만 우리는 **컨텍스트(호스트 루프)가 전이를 수행**하는 형태다.
- **확장 지점**: 인게임 내부 상태(로그인→캐릭선택→인게임, 일시정지)는 같은 패턴을 한 단계 더 적용한다.

### 2.3 퍼사드(Facade) — RenderWorld
- **무엇**: `core::RenderWorld(r, camera, map)` 한 번 호출로 배경 PNG·타일·오브젝트가 일관된 순서로 그려진다. 호출자는 내부 드로우 순서를 몰라도 된다.
- **확장 지점**: 인게임 HUD/이펙트가 늘면 `RenderScene` 류 퍼사드로 묶는다.

### 2.4 템플릿 메서드(Template Method) — HostLoop  ← 이번 리팩토링
- **무엇**: `App::Run()`과 `EditorApp::Run()`에 **글자 그대로 중복**되던 프레임 골격(steady_clock dt 계산, 0.05초 스파이크 클램프, `PollEvents`, `Present`)을 엔진 `core::HostLoop` 기반 클래스로 끌어올렸다. 가변부(장면 전환·오버레이·전역 ESC)는 파생 클래스가 `Frame()` 하나만 구현한다.
- **근거**: ADR-009가 트레이드오프로 적은 "공통 호스트 루프 코드가 두 앱에 중복된다"를 상환한다. dt 클램프 같은 손맛/안정성 값이 한 곳에만 있게 된다.
- **비용**: 가상 호출 1회/프레임(무시 가능), 제어 흐름이 기반 클래스로 한 단계 이동(역전).

## 3. 도입 예정 — 로드맵에 박힌 패턴 (트리거가 명확함)

### 3.1 컴포넌트(Component) — P-005 / ADR-003 ★다음 큰 결정
- **트리거**: 몬스터·스킬을 추가할 때. 상속(`Player : Entity`, `Monster : Entity`)으로 시작하되, "특정 스킬의 상태이상" 같은 **조합 폭증**이 처음 아플 때 전환.
- **형태**: `GameObject`가 `Transform`/`Sprite`/`PlatformerBody`/`Health`/`AIBrain` 등 컴포넌트 리스트를 보유. `PlatformerController`는 이미 사실상 "이동 컴포넌트"라 자연 분해된다.
- **비용(ADR-003 기록 대상)**: 컴포넌트 간 통신·캐시 지역성. 전환 시점과 동기를 ADR-003 증명 과제로 남긴다.

### 3.2 상태(FSM 객체화) — 몬스터 AI — P-005 / `ai/`
- **트리거**: 몬스터 행동이 Idle/Patrol/Chase/Attack/Hurt로 늘어 `if/switch`가 지저분해질 때.
- **형태**: `IMonsterState`(Enter/Update/Exit) + 컨텍스트가 전이. 2.2의 장면 상태와 동형이라 학습 비용이 낮다.
- **주의**: 상태 2~3개일 땐 단순 enum + switch가 더 읽기 쉽다. 4개 이상에서 객체화.

### 3.3 공간 분할(Spatial Partition) — P-007 / ADR-004
- **트리거**: 몬스터·드롭아이템이 늘어 충돌 후보 탐색이 O(n²)로 프레임을 깎을 때. **반드시 벤치마크로 통증을 먼저 측정**(ADR-004 증명 과제).
- **형태**: QuadTree(동적 박스 충돌). 지형 착지는 풋홀드(ADR-008)가 별도로 담당 — 두 모델 공존.
- **비용**: 동적 객체 재삽입 오버헤드. 브루트포스 대비 ms/CPU를 데이터로 비교.

### 3.4 데이터 주도 + 플라이웨이트 — P-006 / ADR-005
- **트리거**: 스킬/몬스터/아이템 수치를 코드에서 뺄 때. `DataManager`가 JSON/CSV를 로드·**캐싱**한다.
- **플라이웨이트 연결**: 몬스터 1000마리가 같은 스펙(공유 상태=스킬 계수·스프라이트 아틀라스)을 **공유**하고, 위치/HP(개별 상태)만 인스턴스가 가진다. 세 글의 "나무 텍스처 공유" 예시가 곧 우리의 스프라이트 아틀라스(ADR-008 증명 과제).
- **비용**: 파싱 예외 처리 난이도(ADR-005 증명 과제).

### 3.5 오브젝트 풀(Object Pool)
- **트리거**: 투사체/타격 이펙트/데미지 텍스트처럼 **매 프레임 생성·소멸**하는 단명 객체가 생길 때.
- **형태**: 최대 개수만큼 미리 생성 → 활성 플래그로 재사용 → 화면 밖이면 반환.
- **주의**: 생성 비용이 측정상 문제될 때만. 풀은 수명 관리 버그(이중 반환)를 새로 들여온다.

## 4. 조건부 — 통증이 생기면 (지금은 아님)

| 패턴 | 도입 신호(이게 보이면) | 그 전까지 대안 |
|------|------------------------|----------------|
| **옵저버 / 이벤트 버스** | HP 변화 하나에 HUD·렌더·주변 몹 등 **다대다**로 반응해야 함 | 직접 호출. 구독 해제 누락 시 누수·순서 의존 버그(세 글이 경고한 단점)를 떠안는다 |
| **커맨드(Command)** | 리플레이 저장, 에디터 **Undo/Redo**, 입력 매크로 | `MoveIntent`로 입력-로직은 이미 분리됨. 명령의 **객체화/기록**이 필요할 때만 승격 |
| **빌더(Builder)** | 맵/몬스터 생성이 다단계이고 **표현이 여러 개**(난이도별) | `BuildDefaultMap` 같은 단순 팩토리 함수 |
| **데커레이터(Decorator)** | 무기/버프 효과를 **런타임에 중첩** (냉기+화염+…) | 컴포넌트(3.1) 또는 효과 리스트 |

> 커맨드 패턴은 키 재바인딩(`InputMap`, [keybinding-system](../.claude/.../memory))과 헷갈리기 쉽다. 현재 키세팅은 **"키→행동(Action) 매핑"** 데이터 모델이지 명령 객체가 아니다. 리플레이/Undo가 생기기 전엔 커맨드로 승격하지 않는다.

## 5. 보류 · 금지 (이 프로젝트에선 비용 > 이득)

### 5.1 싱글톤(Singleton) — 🔴 금지
- **이유**: 우리는 이미 **합성 루트(main)에서 의존성 주입**을 한다(`SDLWindow`/`SDLRenderDevice`를 `App`에 주입). 싱글톤은 이 구조를 깨고 전역 결합·테스트 곤란(세 글 모두 단점으로 지목)을 들여온다.
- **대신**: 의존성 주입(현행) 또는 §5.4 서비스 로케이터(그조차 보류).

### 5.2 방문자(Visitor) — 🔴 보류
- **이유**: 타입군(몬스터/아이템/효과)이 아직 없거나 자주 바뀐다. Visitor는 타입이 **안정**됐을 때만 이득. 지금 넣으면 타입 추가마다 방문자를 다 고쳐야 한다.

### 5.3 컴포지트(Composite) — 🔴 보류
- **이유**: `core::Ui`(메뉴/툴바)가 평면 위젯으로 충분하다. UI가 **중첩 패널 트리**로 깊어질 때 재검토.

### 5.4 서비스 로케이터(Service Locator) — 🔴 보류
- **이유**: 로그/분석/업적 같은 **횡단 서비스가 여럿** 생기기 전엔 DI로 충분. 로케이터는 의존성을 숨겨 추적을 어렵게 한다(싱글톤의 완화판일 뿐).

## 6. 결정 순서도 (패턴을 넣기 전에)

```
변경이 지금 아픈가?  ──No──▶ 넣지 않는다. (가장 흔한 정답)
   │ Yes
   ▼
이미 가진 추상화로 해결되나? (IRenderDevice/Screen/MoveIntent/InputMap)
   │ No
   ▼
통증을 한 문장으로 쓸 수 있나? ("몬스터 상태가 5개라 switch가…")
   │ Yes
   ▼
§1 표에서 그 통증에 대응하는 패턴 1개 선택
   │
   ▼
트레이드오프(비용)를 ADR 또는 이 문서에 적었나? ──No──▶ 적기 전엔 머지 금지
   │ Yes
   ▼
도입. 상태 표(§1) 갱신.
```

## 7. 세 글 ↔ 이 문서 매핑 (출처 정리)

세 글에 중복 등장한 패턴을 하나로 합치고, GuideStory 맥락으로 재배치했다.

- **세 글 공통**: 싱글톤, 상태/FSM, 옵저버, 커맨드, 전략 → 본문 §2~§5에 상태별 배치.
- **1번 글 고유**: 컴포넌트, 빌더, 플라이웨이트.
- **2번 글 고유**: 컴포지트, MVC(= 전략+컴포지트+옵저버 합성이라 단독 패턴으로 다루지 않고 §2.1·§4·§5.3로 분해).
- **3번 글 고유**: 이벤트 버스(옵저버와 §4에서 한 줄에), 오브젝트 풀, 방문자, 데커레이터, 공간 분할, 어댑터, 퍼사드, 서비스 로케이터.

---
*갱신 규칙*: 패턴을 실제로 도입/보류 해제할 때 §1 표의 상태와 관련 ADR을 함께 갱신한다.
