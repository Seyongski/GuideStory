## 0. 목표와 비목표

**목표**

1. 고정된 키워드 집합(사각형·원·삼각형·십자·별·하트)에 대해, **내가 그린 스타일의** 타일 도형을 생성한다.
2. 같은 키워드로 여러 번 뽑으면 **매번 다른 변형**이 나온다 (래스터라이저와 갈라지는 지점).
3. 생성 결과가 **바로 플레이 가능한 맵**이 된다 — 타일뿐 아니라 풋홀드·스폰까지 채운다.
4. 학습 → 추론 → C++ 엔진 반영의 전 과정이 **재현 가능**하다 (ADR-007 증명 과제).

**비목표 (지금은 하지 않는다)**

- 임의의 자연어 문장 해석 ("왼쪽 위에 작은 하트 두 개") — v3 이후.
- 배경·오브젝트·포탈·몬스터 배치 생성 — 타일과 풋홀드만.
- 사진/일러스트 생성 — 별개 트랙 (이 문서 범위 밖).
- 미학적 "좋은 맵" 생성 — 여기서 만드는 건 **도형**이지 레벨 디자인이 아니다.

> **정직한 전제**: 원과 사각형은 20줄짜리 래스터라이저로 그릴 수 있다. 그러니 이 프로젝트의 방어 논리는 "AI 아니면 못 그린다"가 아니라 **"래스터라이저가 못 하는 축에서 AI가 이긴다"** 여야 한다. 그 축이 무엇인지는 §5에서 표로 못 박고, 절차적 래스터라이저를 **베이스라인이자 경쟁 상대**로 항상 함께 측정한다.

## 1. 사용 방식 결정 — "AI 맵 추가" 안이 맞다, 단 즉시 확정은 아니다

두 후보가 있었다.

| | A안 — 에디터 AI 모드 (추천 경로를 보고 내가 그림) | B안 — AI 맵 추가 (키워드+맵이름 → 맵 생성) |
|---|---|---|
| 사용자가 하는 일 | 붓질 전부 | 키워드 입력 |
| 필요한 모델 능력 | **부분 격자 + 라벨 → 나머지 완성** (조건부 인페인팅) | **라벨 → 전체 격자** (무조건부 생성) |
| 난이도 | 상 (B의 능력을 전제로 함) | 중 |
| 실패했을 때 | 그리는 내내 잘못된 고스트가 시야를 방해함 | 결과가 이상하면 그냥 버리면 됨 |
| 데모 임팩트 | 낮음 (결국 내가 그림) | 높음 ("하트" 입력 → 맵이 나타남) |
| 검증 가능성 | 애매 (추천이 좋았는지 정량화 어려움) | 명확 (생성물을 IoU·분류기로 채점) |

### 결정

**B안(AI 맵 추가)을 1차로 구현한다. 단 "생성 즉시 타일 확정"이 아니라 "생성 → 고스트 프리뷰 → 사람이 수락" 흐름으로 만든다.**

이유:

1. **A안은 B안의 상위 과제다.** 부분 격자를 보고 나머지를 채우려면, 애초에 전체를 그릴 줄 알아야 한다. A를 먼저 하면 모델이 도형 개념을 갖기 전에 UI부터 만드는 셈이다.
2. **모델이 나쁠 때 A안은 방해물이 된다.** B안은 결과가 나쁘면 버리면 그만이지만, A안은 그리는 내내 틀린 제안이 화면에 남는다. 검증되지 않은 모델을 편집 동선 한가운데 놓지 않는다.
3. **B안이 기존 데이터 계약과 정렬된다.** ADR-009에서 "맵 파일이 에디터↔게임의 유일한 계약"이라고 정했다. AI의 산출물도 똑같이 `.gsmap` 파일이면, AI는 새로운 결합을 만들지 않고 **기존 계약에 참여하는 또 하나의 생산자**가 된다.
4. **"즉시 확정"만 뺀다.** AI가 파일을 바로 써 버리면 되돌리기가 애매하고, 실패한 생성물이 그대로 자산 폴더에 남는다. 고스트 레이어로 띄우고 사람이 승인하면, ADR-010(§7)의 원칙 — *AI는 제안하고 사람이 결정한다* — 이 UI 수준에서 지켜진다.

### 흡수된 A안

위 결정을 하면 A안의 장점이 자동으로 따라온다. 생성 대상을 "새 맵 전체"가 아니라 **"현재 열린 맵의 선택 영역"** 으로 잡으면 되기 때문이다.

- 빈 맵에서 전체 영역을 선택하고 생성 → 사용자가 말한 **B안 그대로** (맵 이름은 기존 저장 흐름을 그대로 쓴다. AI 전용 저장 경로를 새로 만들지 않는다).
- 작업 중인 맵의 일부 영역을 선택하고 생성 → **내가 만든 맵에 도형을 삽입**.

즉 "AI 맵 추가"는 별도 기능이 아니라 **선택 영역 = 맵 전체인 특수 케이스**다. 메뉴는 하나만 만든다.

### 편집 흐름

```
[에디터] AI 패널 열기 (툴바 → "AI 생성")
   │  키워드 선택(사각형/원/삼각형/십자/별/하트) + 타일 종류 + 영역 드래그
   ▼  SuggestRequest{ label, w, h, seed, tileId }
[AI]  생성
   ▼  SuggestResult{ grid[h][w] }
[에디터] 반투명 고스트로 오버레이 — 아직 맵에 쓰지 않음
   │  R: 다른 seed로 재생성   ←/→: 후보 순환   Esc: 취소
   │  Enter: 수락 → 타일 확정 + 풋홀드 추출(§2.4) + 스폰 배치
   ▼
[에디터] 사람이 손으로 수정 → 저장
   ▼
assets/ai/feedback/  ← 수락/거절/수정본 기록 = 다음 학습 데이터
```

**마지막 줄이 이 설계의 핵심이다.** 사람이 고쳐 놓은 최종본이 곧 다음 세대의 학습 데이터가 된다. 쓸수록 내 스타일에 가까워지는 루프이고, 이게 A안(추천만 보고 내가 그림)이 결코 만들 수 없는 자산이다.

### v2로 미루는 것

A안의 원래 의도 — **"내가 획 몇 개 그으면 AI가 나머지를 완성"** — 은 §4의 v2 자기회귀 모델이 들어온 뒤에 붙인다. 그 모델은 부분 격자를 프리픽스로 받을 수 있어서 인페인팅이 공짜로 따라온다. 지금 CVAE로 억지로 만들 이유가 없다.

## 2. 표현과 데이터 계약

### 2.1 정규 격자 (모델의 세계)

모델은 맵 크기를 모른다. **32×32 정규 격자** 하나만 다룬다.

- 각 셀 = 타일 클래스 `0..5` (0 = 빈 칸, 1..5 = [`core::TilePalette`](../GuideStory/src/core/TilePalette.h)의 흙/풀/돌/나무/물)
- 에디터가 선택 영역 크기로 **최근접 리샘플**해서 붙인다.

이렇게 나누면 맵 크기·타일 팔레트 확장이 모델 재학습을 강제하지 않는다. 팔레트가 50종으로 늘면 그때 출력 차원만 늘린다.

### 2.2 라벨

v1은 **닫힌 집합**이다. 자유 텍스트를 받지 않는다.

| id | 라벨 | 동의어(에디터가 매핑) | 합성 시드 |
|----|------|----------------------|-----------|
| 0 | 사각형 | 네모, 정사각형, square | ✅ |
| 1 | 원 | 동그라미, 원형, circle | ✅ |
| 2 | 삼각형 | 세모, triangle | ✅ |
| 3 | 십자 | 크로스, 더하기, cross | ✅ |
| 4 | 별 | 스타, star | ✅ |
| 5 | 하트 | 하투, heart | ❌ **손그림만** |

동의어 매핑은 v1에서 **에디터의 문자열 테이블**이 처리한다. 모델은 id만 받는다. 미등록 단어는 "모르는 키워드"로 거절하고, 추측하지 않는다.

> **하트에 합성 시드를 주지 않는 이유는 §3.3의 증명 설계 때문이다.** 실수가 아니다.

### 2.3 맵 포맷 확장 (`GSMAP 3`)

생성물의 출처를 파일에 남긴다. 재현성이 없으면 "AI가 만들었다"를 증명할 수 없다.

```
GSMAP 3
...
CONCEPT heart                      # 이 맵의 라벨 (학습 데이터 수집 시 사용)
AIGEN cvae_v1 heart 20260828 3     # 모델명 / 라벨 / seed / 리비전
```

- `CONCEPT`는 **손으로 그린 맵에도** 붙인다. 학습 데이터의 라벨이 곧 이 줄이다.
- `AIGEN`은 AI가 생성한 맵에만. 사람이 손대면 `AIGEN ... edited` 로 마킹한다 — 순수 생성물과 사람이 고친 것을 학습에서 구분해야 한다.
- **선행 작업**: 버전을 올리기 전에 파서가 **모르는 헤더 키를 건너뛰도록** 먼저 고친다. 그래야 다음에 키를 추가할 때 또 버전을 올리지 않는다.

### 2.4 풋홀드 추출 — 도형을 "놀 수 있게" 만든다

ADR-008에 따라 **타일은 코스메틱이고 충돌은 풋홀드**다. 그러니 타일 격자만 생성하면 맵이 아니라 그림이다. 생성 파이프라인의 마지막 단계는 격자 → 선분 변환이다.

1. **표면 셀 추출**: 타일이 있고, **바로 윗 칸이 빈 칸**인 셀만 고른다.
2. **가로 런 병합**: 같은 행에서 연속된 표면 셀을 하나의 수평 선분으로 묶는다.
3. **경사 병합**: 이웃한 런의 y가 정확히 1칸 차이면 두 선분을 하나의 **경사 선분**으로 잇는다. 원·하트의 곡면이 계단이 아니라 경사가 되고, 메이플식 경사 보행이 자연스럽게 나온다.
4. **길이 필터**: 1칸짜리 파편 선분은 버린다 (걸리적거리는 턱이 된다).
5. **스폰 배치**: 가장 긴 선분의 중앙 위에 `SPAWN`.

옵션 하나를 둔다 — **윤곽만 발판 / 전체 표면 발판**. 하트 안쪽까지 다 밟히면 도형이 안 보인다.

> 이 단계는 AI가 아니라 결정론적 후처리다. 모델에게 풋홀드까지 생성시키지 않는다 — 학습 데이터가 몇십 배 더 필요해지는데, 규칙으로 정확히 풀리는 문제다.
>
> **어디에 두는가: C++ 에디터(정본).** 수락 시점에 에디터가 타일을 확정하므로 같은 자리에서 풋홀드도 만든다. 파이썬이 만들면 프로토콜이 격자+풋홀드를 함께 실어야 해서 계약이 지저분해지고, 에디터가 이미 가진 풋홀드 편집 코드를 재사용하지 못한다. 파이썬 쪽 `tools/footholds.py`는 **평가 지표(플레이 가능성) 계산용 재구현**이며, `gsmap.py`가 `Map.cpp`를 미러링하는 것과 같은 이중 관리 위험을 진다 — 같은 격자 입력에 대한 출력 비교 테스트로 방어한다.

## 3. 데이터 — 이 프로젝트의 진짜 난관

모델이 아니라 데이터가 병목이다. 지금 리포에 맵은 2개뿐이다.

### 3.1 3층 구조

| 층 | 출처 | 규모 | 역할 |
|---|---|---|---|
| **합성(synth)** | `synth_shapes.py` 절차적 래스터라이저, 파라미터 랜덤화 | 라벨당 2,000 | 사전학습 — 도형의 큰 틀을 잡는다 |
| **손그림(raw)** | 내가 에디터로 그린 `.gsmap` | 라벨당 15~40 | 파인튜닝 — **내 스타일**이 여기서 들어온다 |
| **피드백(feedback)** | AI 생성 후 사람이 수정한 최종본 | 사용할수록 증가 | 재학습 — 데이터 플라이휠 |

**합성 사전학습 → 손그림 파인튜닝** 이 순서를 지킨다. 반대로 하면 손그림 40장의 특징이 합성 2,000장에 묻힌다.

### 3.2 증강 정책 (라벨별로 다르다)

| 증강 | 사각형 | 원 | 삼각형 | 십자 | 별 | 하트 |
|---|---|---|---|---|---|---|
| 평행이동 ±4칸 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 좌우 반전 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 상하 반전 | ✅ | ✅ | ❌ | ✅ | ✅ | ❌ |
| 90° 회전 | ✅ | ✅ | ❌ | ✅ | ❌ | ❌ |
| 스케일 0.7~1.3 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 윤곽 두께 ±1 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 셀 드롭아웃 3% | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

**뒤집은 하트는 하트가 아니고, 회전한 삼각형은 삼각형으로 안 보인다.** 증강을 라벨과 무관하게 일괄 적용하면 모델에게 거짓말을 가르치게 된다. 이 표 자체가 문서화 가치가 있는 결정이다.

### 3.3 증명 설계 — 하트 홀드아웃

가장 흔한 반론은 **"결국 네가 만든 래스터라이저를 흉내 낸 것 아니냐"** 다. 이걸 미리 차단한다.

> **하트는 절차적 합성 데이터를 한 장도 주지 않는다.** 손으로 그린 15~40장이 전부다.
> 그런데도 모델이 하트를 안정적으로 생성한다면, 그건 래스터라이저 모방이 아니라 **적은 샘플에서 형태를 학습한 것**이다.

부가 증명 두 가지:

- **라벨 임베딩 보간**: 사각형↔원 임베딩을 선형 보간해 생성하면, 중간에서 모서리가 둥글어지는 연속 변화가 나와야 한다. 잠재 공간을 학습했다는 시각적 증거이고, 포트폴리오에 넣을 그림이 여기서 나온다.
- **잠재 변수 샘플링**: 같은 라벨·다른 `z`로 50장을 뽑아 전부 다르되 전부 알아볼 수 있어야 한다 (모드 붕괴 검사).

## 4. 모델 로드맵

### v1 — 조건부 VAE (Conditional VAE) ★ 여기서 시작

```
Encoder: grid(32×32, 6채널 one-hot) ⊕ label_emb(16)
         → Conv 3×3 [32→64→128], stride 2, BN+ReLU
         → FC → μ, logσ²      (z 차원 16)
Decoder: z(16) ⊕ label_emb(16)
         → FC → ConvTranspose [128→64→32]
         → 32×32×6 logits
Loss:    CrossEntropy(재구성) + β·KL      (β는 0→1 워밍업)
```

- 파라미터 **약 30만 (~1.2MB)**. GPU 없이 CPU로 10~20분이면 학습된다.
- 생성 지연 **5ms 미만** — 에디터에서 즉시 반응한다.
- **왜 CVAE인가**: (a) 작은 데이터셋에서 GAN보다 훨씬 안정적이다. 손그림 40장으로 GAN을 돌리면 모드 붕괴가 거의 확정이다. (b) `z` 샘플링이 곧 "변형 생성"이라 §0의 목표 2가 구조적으로 따라온다. (c) 잠재 공간 보간이 §3.3의 증명 그림을 공짜로 준다.
- **한계(정직하게)**: VAE 출력은 뭉개지는 경향이 있다. 격자가 32×32로 거칠고 출력이 이산 클래스라 픽셀 이미지만큼 심하진 않겠지만, 윤곽이 흐릿하면 **argmax 대신 온도 샘플링 + 최대 연결 컴포넌트만 남기는 후처리**로 다듬는다.

### v2 — 자기회귀 트랜스포머 (내가 만든 초소형 LLM)

```
토큰:   [LABEL] + grid를 row-major로 펼친 1,024 토큰 (어휘 6 + 특수토큰)
구조:   4 layer, d_model 128, 4 head, causal mask, 학습된 위치 임베딩
파라미터: 약 80만
```

- **얻는 것**: 부분 격자를 프리픽스로 넣으면 나머지를 이어 그린다 → §1의 A안(획 몇 개 → 자동 완성)이 여기서 열린다. temperature/top-k로 "얼마나 과감하게"를 조절할 수 있다.
- **비용**: 1,024 토큰 순차 생성이라 수십~수백 ms. 클릭당 1회면 허용 범위지만 실시간 고스트에는 무겁다 → **v1(CVAE)로 즉시 초안, v2(AR)로 정밀 완성**이라는 2단 구성이 자연스럽다.
- 이 단계가 "로컬 LLM을 직접 만들어 학습시켰다"의 실체가 된다. 남의 7B 모델을 불러 쓴 것이 아니라, **토크나이저부터 어텐션까지 내가 정의한 생성 모델**이다.

### v3 이후 — 자연어 조건 레벨 생성

닫힌 라벨을 벗어나 `"차가운 얼음동굴, 아래쪽은 물, 발판은 드문드문"` 같은 문장을 받는 단계다. **이건 v1/v2의 확장이 아니라 별개 과제**이므로 문서를 분리했다 — [ai-level-generation.md](ai-level-generation.md).

한 줄 요약: 여기서 처음으로 **기성 로컬 LLM**이 등장하지만 역할은 딱 하나, **자연어 → `MapSpec` JSON 변환**이다. 타일을 놓는 건 끝까지 내가 학습시킨 모델이고, LLM은 에디터의 조건 위젯을 대신 채워주는 입력 보조 장치일 뿐이다.

## 5. 평가 — 베이스라인과 나란히 잰다

### 5.1 지표

| 지표 | 정의 | v1 목표 |
|---|---|---|
| 형태 정확도 | 최적 정렬 후 레퍼런스 도형과의 IoU | 사각형·원 ≥ 0.75 |
| 인식률 | **별도로 학습한 분류기**가 생성물의 라벨을 맞히는 비율 | ≥ 0.90 |
| 다양성 | 같은 라벨 50장의 pairwise 해밍 거리 평균 | 0.05~0.25 (붕괴도 노이즈도 아님) |
| 연결성 | 최대 연결 컴포넌트 / 전체 타일 수 | ≥ 0.95 |
| 플레이 가능성 | 추출된 풋홀드로 스폰→최상단 도달 가능 | 라벨당 ≥ 0.8 |
| 생성 지연 | 요청→결과 왕복 (ms) | IPC / libtorch 각각 측정 |

인식률에 쓰는 분류기는 **생성 모델과 별도로, 손그림 데이터로만** 학습한다. 생성기와 같은 데이터·같은 특징을 쓰면 자기 채점이 된다.

### 5.2 절차적 래스터라이저 대비 (반드시 함께 싣는다)

| 축 | 래스터라이저 | 학습 모델 | 승자 |
|---|---|---|---|
| 형태 정확도 | 완벽 (정의상) | 0.75~0.9 | **래스터라이저** |
| 구현 비용 | 20줄 | 파이프라인 전체 | **래스터라이저** |
| 생성 지연 | µs | ms | **래스터라이저** |
| 변형 다양성 | 파라미터 랜덤화 범위 안에서만 | 잠재 공간 샘플링 | **모델** |
| 미학습 도형 확장 | 도형마다 코드 추가 | 예시 15장 추가 | **모델** |

**래스터라이저가 이기는 칸을 지우지 않는다.** 트레이드오프를 정직하게 적는 것이 이 리포의 규칙이고([ARCHITECTURE.md](../ARCHITECTURE.md) §4), 면접에서 "왜 AI를 썼나"에 답하는 근거도 결국 이 표다.

## 6. 시스템 통합

### 6.1 C++ 모듈 (`GuideStory/src/ai/`)

ADR-006(SDL 디커플)과 같은 패턴이다. 엔진은 인터페이스만 알고, **AI가 없어도 에디터는 완전히 동작해야 한다**.

```
src/ai/
├─ AiTypes.h          # ShapeRequest / ShapeResult (POD, 외부 의존 0)
├─ IShapeGenerator.h  # 추상 인터페이스 — Generate(req) → result
├─ NullShapeGenerator.h   # 폴백. AI 미연결 시 빈 결과 + "AI 없음" 표시
├─ RemoteShapeGenerator.* # 1단계: 소켓+JSON으로 Python 추론 서버 질의
└─ TorchShapeGenerator.*  # 2단계: libtorch로 .pt 직접 로드 (#ifdef GUIDESTORY_WITH_TORCH)
```

- **`net/Framing.cpp`를 재사용한다.** 길이 프리픽스 프레이밍과 상한 검사를 이미 직접 짜뒀다(ADR-001). AI 채널도 같은 계약을 쓰면 프레이밍 설계가 두 서브시스템에서 검증된다.
- **스레드 모델은 `NetClient`와 동일**: 추론은 워커 스레드, 에디터 스레드는 결과 큐만 폴링. 생성 중에도 프레임이 멈추지 않는다.
- 서버 접속 주소를 `assets/config/server.txt`에서 읽듯, AI 주소는 `assets/config/ai.txt`(기본 `127.0.0.1:7788`). 파일이 없으면 오류가 아니라 `NullShapeGenerator`로 폴백한다.

### 6.2 두 단계 통합 (ADR-007 증명 과제)

| 단계 | 방식 | 얻는 것 | 비용 |
|---|---|---|---|
| 1 | Python 추론 서버 + 소켓 | 모델 교체가 C++ 재빌드 없이 됨. 학습 루프와 같은 코드로 추론 | 프로세스 간 왕복 지연, 서버 기동 필요 |
| 2 | TorchScript `.pt` + libtorch 인프로세스 | 지연 최소, 단일 실행파일 배포 | 빌드 복잡도(libtorch 링크), 바이너리 크기 |

**둘 다 만들고 같은 인터페이스 뒤에 놓는다.** 그래야 "IPC vs 인프로세스 지연 비교표"라는 ADR-007의 증명 과제가 데이터로 나온다. 하나만 만들면 비교가 없다.

## 7. ARCHITECTURE.md에 추가할 ADR 초안

> 아래 3개는 검토 후 [ARCHITECTURE.md](../ARCHITECTURE.md) §4에 옮기고, §5 증명 대시보드에 행을 추가한다.

### ADR-010 — AI는 제안하고, 사람이 확정한다

- **결정**: AI 생성 결과를 맵에 직접 쓰지 않는다. 항상 고스트 레이어로 표시하고 사람의 수락(Enter)이 있어야 타일이 된다. 수락·거절·수정 이력을 기록한다.
- **이유**: 검증되지 않은 모델이 자산을 직접 변경하면 되돌리기가 어렵고 실패작이 파일로 남는다. 그리고 사람이 고친 최종본이 다음 학습 데이터가 되어야 데이터 플라이휠이 성립한다.
- **트레이드오프**: 자동화 이득 일부 포기(키워드 한 번에 완성 파일이 나오지 않는다). 에디터에 고스트 레이어·후보 순환 UI가 추가로 필요.
- **증명 과제**: 피드백 로그로 재학습했을 때 인식률·다양성 지표가 개선되는지 세대별로 기록.

### ADR-011 — 생성 모델과 결정론적 후처리를 분리한다

- **결정**: 신경망은 **타일 격자**만 생성한다. 풋홀드 추출·경사 병합·스폰 배치·연결성 정리는 규칙 기반 후처리가 맡는다.
- **이유**: 풋홀드까지 학습시키려면 데이터가 수십 배 필요한데, 규칙으로 정확히 풀리는 문제다. 실패 지점도 분리된다 — 도형이 이상하면 모델 탓, 못 밟으면 후처리 탓.
- **트레이드오프**: 후처리 규칙이 도형 종류를 타면 규칙이 늘어난다. 모델이 "발판으로 쓰기 좋은 형태"를 학습할 기회를 포기한다.
- **증명 과제**: 후처리 전후 플레이 가능성 지표 비교. 후처리 규칙 수가 도형 추가에 따라 어떻게 늘어나는지 추적.

### ADR-012 — 라벨은 닫힌 집합에서 시작한다

- **결정**: v1은 6개 고정 라벨 + 에디터의 동의어 문자열 테이블. 자유 텍스트 입력을 받지 않는다. 텍스트 임베딩 조건화는 v3.
- **이유**: 자유 텍스트를 받는 순간 "무엇을 맞혔는지" 채점할 수 없다. 닫힌 집합이어야 §5의 지표가 정의된다.
- **트레이드오프**: 미등록 키워드가 거절된다(추측하지 않는다). 라벨 추가마다 학습 데이터가 필요.
- **증명 과제**: v3 전환 시, 미학습 표현("동그라미", "둥근 언덕")의 매핑 성공률 측정.

## 8. 마일스톤

**단일 출처는 [ai-roadmap.md](ai-roadmap.md) §4다.** 여기서 중복 관리하지 않는다.

이 문서가 다루는 범위는 **P-010 ~ P-017 (게이트 G0~G3)** 이고, 그중 순서상 주의할 점만 옮겨 적는다.

- **G0(P-010~013)이 먼저다.** 모델보다 **에디터↔파이썬 관통**을 먼저 뚫는다. 이때 파이썬 쪽은 학습 모델이 아니라 **절차적 래스터라이저 스텁**이다 — ML 위험 없이 전 경로를 검증하고, 그 래스터라이저는 §5.2 베이스라인과 §3.1 합성 데이터 생성기로 그대로 승격된다.
- **`GSMAP 3`(§2.3)는 G0에서 넣는다.** `CONCEPT` 없이 손그림을 쌓으면 나중에 전부 다시 라벨링해야 한다.
- **P-017(libtorch)까지가 "AI 서브시스템 통합"의 완성**이다. ADR-007이 여기서 `☑`가 된다.

## 9. 리스크와 열린 질문

| 리스크 | 징후 | 대응 |
|---|---|---|
| 손그림 데이터 부족 | 하트만 인식률이 낮게 고정 | 라벨당 40장까지 늘리고, 그래도 안 되면 하트에 한해 합성 시드 허용 — **단 그 사실을 리포트에 명시** |
| VAE 출력 뭉개짐 | 윤곽이 흐리고 연결성 지표 하락 | 온도 샘플링 + 최대 연결 컴포넌트 후처리. 그래도 안 되면 v2를 앞당김 |
| 모드 붕괴 | 다양성 지표가 0에 수렴 | β 워밍업 재조정, `z` 차원 축소, 증강 강도 상향 |
| "래스터라이저 모방" 비판 | — | §3.3 하트 홀드아웃 + 라벨 보간 그림으로 선제 대응 |
| 32×32 해상도 부족 | 하트 곡선이 계단으로만 표현됨 | 48×48로 상향(파라미터·학습시간 증가). 격자 크기를 설정으로 빼둔다 |

**아직 정하지 않은 것**

- 생성 시 타일 종류를 **사용자가 고르게** 할지, **모델이 라벨과 함께 학습**하게 할지. v1은 사용자 선택(단순), 데이터가 쌓이면 재검토.
- 고스트 후보를 몇 개 미리 뽑아 둘지 (1개 + 재생성 vs 4개 동시 표시). 4개 동시가 선택 품질은 높지만 화면이 복잡해진다.
- 피드백 로그의 개인 편향 — 내 취향만 강화되어 도형이 무너질 수 있다. 세대별 인식률을 감시 지표로 둔다.
